# Migration guide: 0.3.x

Run `agent-runner migrate` before you upgrade — it rewrites removed/renamed
config fields to their current form in one pass, the same convention as the
0.2.x guide. See `CHANGELOG.md` for the exhaustive per-change list; this file
covers what `migrate` does automatically, the one thing it cannot do, and the
exact boot-gate errors an operator will see.

---

## Upgrading to 0.3.0 (breaking) — run `agent-runner migrate`

0.3.0 collapses the plugin ABI to one entry-point group and regroups
`[monitor.host_health]`. **Run `agent-runner migrate` before you upgrade**,
fix any `MANUAL:` line it prints, then upgrade.

**What `migrate` rewrites automatically:**

- **`[monitor.host_health]`'s 9 flat keys relocate** into `.disk`/`.memory`/
  `.pressure` sub-tables (see `CHANGELOG.md` for the full old→new key list).
- **`round_timeout_s` renames to `round_budget_s`**, in `[runtime]` and every
  `[phases.<name>]` flat/nested form.
- **`schema_version = 1` is stamped** as the file's first line once every
  other rewrite above has converged — a migrated config never needs this run
  again.

**What `migrate` cannot rewrite: external plugin code.** The plugin ABI moved
from seven separate entry-point groups (`agent_runner.pre_round_hooks`,
`post_round_hooks`, `dirty_handler_hooks`, `detectors`,
`serve_startup_hooks`, `context_enrichers`, `event_kinds`) plus an import-time
`register_*()` call, to one group — `agent_runner.plugins` — resolving a
single typed `PluginManifest` per plugin. `migrate` can rename config keys; it
cannot rewrite a third-party plugin module's Python. If you forked one of the
six builtins as a template, port it by hand using the old hook-level name →
new manifest name mapping below:

| Old (0.2.x hook-level name) | New (`PluginManifest.name`) |
|---|---|
| `claude_error_detector` (`post_round_hooks` group) | `claude` |
| `gemini_error_detector` | `gemini` |
| `codewhale_error_detector` | `codewhale` |
| `kimi_error_detector` | `kimi` |
| `pi_error_detector` | `pi` |
| `default_dirty_handler` (`dirty_handler_hooks` group) | `default_dirty_handler` (unchanged) |

Shape change, bottom-of-file → module-level:

```python
# 0.2.x
register_post_round_hook(ClaudeErrorDetector())

# 0.3.0+ (name became "claude" in 0.3.9 — see the 0.3.9 note below)
PLUGIN = PluginManifest(
    name="claude",
    post_round_hooks=(ClaudeErrorDetector(),),
)
```

`pyproject.toml` entry-points collapse from seven groups to one:

```toml
# 0.2.x
[project.entry-points."agent_runner.post_round_hooks"]
my_plugin = "my_pkg.plugin:MyDetector"

# 0.3.0
[project.entry-points."agent_runner.plugins"]
my_plugin = "my_pkg.plugin:PLUGIN"
```

**`[plugins] disable` now keys on the plugin's manifest name, not the
individual hook's name.** If you set `disable = [...]` against an old
hook-level name, rewrite it using the same mapping table above (identical to
the one `migrate` prints for this exact shape):

| Old name in `disable = [...]` | New name |
|---|---|
| `claude_error_detector` | `claude` |
| `gemini_error_detector` | `gemini` |
| `codewhale_error_detector` | `codewhale` |
| `kimi_error_detector` | `kimi` |
| `pi_error_detector` | `pi` |

**0.3.9 — the claude plugin was renamed `claude_rate_limit` → `claude`** (its
manifest + entry-point name) so its `cooperative_stop`/`sigterm_grace_s` join
onto the `claude` agent binary — the module file stays `claude_rate_limit.py`. A
config with `disable = ["claude_rate_limit"]` must switch to `["claude"]`;
`migrate` flags this as a manual rename (it does not rewrite a `disable` list
element).

`migrate` detects a stale hook-level name here but does NOT rewrite it for
you (it's flagged MANUAL, not applied) — a `disable = [...]` entry is a bare
string with no table/key context to anchor a safe automatic rewrite. Leaving
the old name in place does not fail loudly: the config still loads, but the
disable silently no longer matches any registered plugin, so the "disabled"
plugin keeps running. You'll see a `UserWarning` naming the unmatched entry
when `serve`/`round` starts — if you see it, rename the entry by hand using
the table above.

**The `schema_version` boot gate.** A config that predates this release, or
was hand-edited without a `schema_version` key, is now rejected at load
rather than partially trusted. The exact errors:

- Missing `schema_version`: `config predates schema_version — run 'agent-runner migrate'`
- Non-integer `schema_version`: `schema_version must be an integer, got <value>`
- Older than this build supports: `config schema_version <N> is older than this agent-runner supports — run 'agent-runner migrate'`
- Newer than this build supports (a downgrade): `config schema_version <N> is newer than this agent-runner supports (max <M>) — upgrade agent-runner`

Any of these means the same fix: run `agent-runner migrate` (or, for the
newer-than-supported case, upgrade the `agent-runner` package instead).
