# Migration guide: 0.2.8

## TL;DR

**New `agent-runner migrate` command rewrites outdated config fields to their
current form, and `upgrade` now runs that migration automatically.** A config
written for an older release — using a field that was later renamed or removed —
no longer has to be edited by hand before it loads. Removed-field errors now end
with a hint to run `agent-runner migrate`. No public symbols were removed; one new event
kind (`config_migrated`) and one new flag (`upgrade --no-migrate`).

---

## What `migrate` does

    agent-runner migrate [--dry-run]

Reads the config resolved from `--config` (default `./agent-runner.toml`),
applies each known transform, and writes the result **in place** with a `.bak`
backup of the original. It prints one line per change; fields it cannot rewrite
automatically are reported as `MANUAL:` lines. A config with nothing to change
is left untouched (and no `.bak` is written).

`--dry-run` prints the same report without writing the file or the backup.

### Exit codes

| Code | Meaning |
|---|---|
| `0` | config was clean, or every needed change was applied |
| `1` | a `MANUAL:` change remains (nothing auto-applied can fix it) |
| `2` | config could not be read, or is not valid TOML |

## The transforms

| Old field | Action | New form |
|---|---|---|
| `runtime.rate_limit_action` | auto-rename | `runtime.transient_error_action` (same values: `back_off` / `skip` / `stop`) |
| `vcs.orphan_action` | auto-rename | `vcs.dirty_action` (same values: `stash` / `ignore` / `auto_commit`) |
| `runtime.round_timeout_per_phase` | **manual** | move each entry to `[phases.<name>]` `round_timeout_s = X` |

The two renames are targeted text rewrites — they preserve the rest of the file
(comments, ordering, formatting) and only touch the key name. The
`round_timeout_per_phase` removal (0.1.16) changed the shape of the value, not
just its name, so it is reported as a `MANUAL:` line rather than rewritten.

## `upgrade` runs it automatically

`agent-runner upgrade` migrates the config **before** it touches the package or
the service:

- Auto-applicable renames are rewritten in place (with `.bak`), and a
  `config_migrated` event records the applied changes and the config path.
- A field needing a **manual** change aborts the upgrade **before** it stops the
  service or installs anything — the run fails fast with the `MANUAL:` lines, so
  a still-un-migratable config can never leave the service stopped mid-upgrade.
  Fix it (or run `agent-runner migrate`) and retry.
- `agent-runner upgrade --no-migrate` skips the step entirely.

## `config_migrated` event

Emitted by `upgrade` after it rewrites the config *and* the migrated config
loads successfully. Lands in the normal event stream (`events-YYYY-MM.jsonl`).
In the rare case where the rewrite happens but an unrelated `ConfigError`
prevents the config from loading, no event fires.

| Field | Meaning |
|---|---|
| `applied` | list of applied transform descriptions |
| `manual` | list of manual-change descriptions — always `[]` when this event fires (a manual-only migration aborts before emitting) |
| `path` | the config file that was rewritten |

## Nothing to change on a clean config

- A config that already uses the current field names migrates to a no-op:
  `migrate` prints `nothing to migrate` and exits `0`, and `upgrade` proceeds
  normally.
- The `.bak` backup lets you revert a migration by restoring
  `agent-runner.toml.bak` over `agent-runner.toml`.
