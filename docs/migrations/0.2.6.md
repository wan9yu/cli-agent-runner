# Migration guide: 0.2.6

## TL;DR

**0.2.4 and 0.2.5 could delete your agent transcripts without saying so.** This
release stops that. No public symbols removed, no config changes needed, one
new event kind (`round_logs_prune_deferred`). If you are still on ≤0.2.3 with a
large `{log_dir}/rounds/` backlog, upgrade **straight to 0.2.6** — going via
0.2.4 or 0.2.5 runs the silent deletion once, and 0.2.6 does not.

---

## The bug: a silent first-contact deletion of `rounds/`

0.2.4 started pruning `{log_dir}/rounds/R<N>-*.log` — the agent's own
transcripts — to `runtime.round_log_retention` (default **100**) at the start
of every round. That family had grown unbounded since it was introduced, so the
prune's *first* pass on any long-running deployment was not a prune: it was the
deletion of the entire backlog, in one shot, with nothing emitted and nothing
logged. The count of deleted files was returned by the pruning function and
discarded by its caller.

The scale is not theoretical. One deployment reported 12,293 transcripts /
6.5 GB, oldest `R1-20260520T023025.log`, `round_log_retention` never
configured. Their first post-upgrade round would have deleted 12,193 files —
about 6.4 GB, the complete history since R1 — on a host with 856 GB free. These
are not "logs" in the rotate-and-forget sense; they are the record you
reconstruct a round from after a dropped connection, and the corpus you grep to
find a flaky test's trigger condition.

## The fix: bulk prunes delete nothing and report

From 0.2.6, a prune that would delete **more files than it keeps** is a *bulk*
prune, and a bulk prune deletes nothing. It emits `round_logs_prune_deferred`
and leaves every file in place. In steady state a round retires about one file,
so the guard cannot trip during normal operation — only on a first encounter
with a pre-existing backlog, or after retention is lowered far below the
current file count.

The guard never blocks or fails a round: it defers a deletion, nothing else.
The round runs, `serve` starts, everything else is unchanged.

`round_logs_prune_deferred` payload:

| Field | Meaning |
|---|---|
| `directory` | the directory whose prune was deferred |
| `existing` | matching files present |
| `keep` | `runtime.round_log_retention` as configured |
| `would_delete` | files a normal prune would have removed |
| `hint` | one line naming the knob to turn |

It is re-emitted on every prune attempt while the condition holds — the
deferral is permanent until an operator acts, and a one-shot event would be
invisible to anyone who started watching later.

## What you should do

**Nothing, unless you see the event.** When you do, you have two options:

- **Raise `[runtime] round_log_retention`** to at least the reported
  `existing`. The backlog then fits inside the kept window, nothing is deleted,
  and normal per-round pruning resumes once the count grows past the new value.
- **Delete or archive the files yourself** from the reported `directory`. The
  next prune sees a count the guard no longer calls bulk and resumes.

Until you choose, the family grows unbounded — the same growth you had before
0.2.4, except now it is announced instead of silent. There is deliberately no
config knob to re-enable bulk deletion: the supervisor does not delete history
in bulk on its own.

## Where you stand, by current version

- **On ≤0.2.3** — you have never had `rounds/` pruned, so your backlog is
  intact. Upgrade directly to 0.2.6 and it stays intact; the first round emits
  `round_logs_prune_deferred` and deletes nothing. (Upgrading via 0.2.4 or
  0.2.5, even briefly, performs the deletion.)
- **On 0.2.4 or 0.2.5** — the deletion has already happened; the files are
  gone and 0.2.6 cannot bring them back. What it prevents is a repeat: lowering
  `round_log_retention` later can no longer wipe the intervening history.

## Also in this release

The guard covers the serve-level `{log_dir}/round-<N>.log` family too, pruned
at serve startup. No release ever introduced a backlog there — that family has
been pruned since it was introduced — but a single knob governs both, so
lowering `round_log_retention` now means the same thing in both places.
`agent_runner.round_log.prune_rounds_dir` and `prune_old_round_logs` return a
`PruneOutcome` (`deleted`, `deferred`, `existing`) instead of `int` / `None`;
both are internal helpers, not part of the pinned public API surface.
